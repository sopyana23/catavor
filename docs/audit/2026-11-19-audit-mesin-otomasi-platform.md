# Audit bot dan halaman Mesin Otomasi Catavor

**19 November 2026 · Revisi sumber `7c91dfe` · Admin pengelola platform**

## Kesimpulan untuk pengelola

| Pertanyaan | Hasil audit |
|---|---|
| Apakah semua bot tercantum? | **Belum.** Pada ketiga frontend, katalog berisi **11 dari 13 ID awal tracker**. Dua ID yang hilang adalah `storage_sweeper` dan `market_intel_worker`. Keduanya memiliki jadwal dan handler manual di Go. Antrean email, siklus langganan, eskalasi moderasi, dan beberapa pekerja telemetri bahkan belum memiliki entri tersendiri di tracker. |
| Apakah semua yang berlabel aktif benar-benar berjalan berkala? | **Belum dapat disimpulkan dari halaman.** Ada 16 loop pekerja aplikasi yang bisa ditelusuri dari startup. Angka ini berbeda satuan dari jumlah kartu. Promo, flash sale, dan ringkasan mingguan memiliki handler manual, tetapi penjadwal sesuai frekuensi yang dijanjikan kartu tidak ditemukan. |
| Apakah ketentuan dan dampak tombol cukup jelas? | **Belum.** Misalnya, “Kedaluwarsa Toko” menjalankan dormansi, pembersihan notifikasi juga memproses sesi, dan “SLA Tiket” dapat ikut memusnahkan tiket lama beserta lampiran. |
| Apakah ada sandbox? | **Ada tab Sandbox.** Tes panduan menulis notifikasi sungguhan untuk akun penguji dan menyiarkannya melalui SSE. Sejumlah tombol “Simulasi” lain memanggil proses operasional pada database aplikasi. **Prioritas pertama adalah menarik tombol eksekusi nyata dari area latihan.** |
| Apakah API sama di mobile, tablet, laptop, dan desktop? | **Ya untuk halaman Mesin Otomasi.** Semua membaca status dan log serta memicu aksi lewat tiga rute Go yang sama. **Paritas fungsi belum penuh.** Tablet memiliki dua simulasi tambahan, salah satunya mengirim aksi yang tidak didukung server. Hak akses UI dan server juga berbeda pada semua perangkat. |

### Cara membaca inventaris

Urutan 1–13 mencocokkan setiap ID tracker dengan kartu dan pelaksananya. Urutan 14–25 mencakup proses backend tambahan. Tabel berikutnya memuat pekerjaan singkat berbasis peristiwa dan otomasi infrastruktur. Satu loop dapat mengerjakan beberapa fungsi dan dua tombol dapat memanggil fungsi yang sama. Karena itu, menjumlahkan baris tabel tidak menghasilkan jumlah daemon.

Audit menelusuri startup Go, semua pemakaian ticker dan goroutine pada kode aplikasi, pemanggil fungsi siklus, rute dan izin, serta komponen portal yang dirender. Perbandingan otomatis himpunan ID dilakukan atas ketiga array kartu. Inspeksi Chromium memakai bundle lokal dengan respons API sintetis. Tidak ada pemicu operasional yang dikirim ke backend aktif. Jadwal di bawah berarti **terhubung dalam kode**. Aktivitas terakhir, volume, instalasi timer host, dan kesehatan produksi memerlukan pengukuran pada deployment. [Startup server](../../backend/cmd/server/main.go#L108) · [Registri dan tracker](../../backend/internal/services/automation_service.go#L69)

## 3. Apa yang sebenarnya dilakukan Sandbox

| Tombol | Perangkat | Jalur efektif dan dampak |
|---|---|---|
| Kirim notifikasi panduan uji | Semua | `test_guide` membuat satu record notifikasi bertarget akun admin, dengan kedaluwarsa 48 jam, mengirim lewat hub SSE, dan menulis log sandbox. Respons sukses menyatakan server menerima pengiriman. Tidak ada tanda terima dari layar penerima. Durasi log diisi angka tetap 12 ms. |
| Simulasi Toko/Merchant Expired | Semua | Mengirim `store_expiry` ke handler operasional. Dapat mengubah status, mengirim pemberitahuan, atau menghapus data jika kandidat dormansi memenuhi syarat. |
| Simulasi Dormansi | Semua | Mengirim `dormancy_worker` ke fungsi yang sama dengan tombol sebelumnya. Cakupannya seluruh kandidat yang ditemukan di database. |
| Simulasi Promo Expired | Semua | Menghitung toko dengan banner pada data aplikasi dan menulis log/heartbeat. Hasilnya tidak membuktikan perubahan status promo. |
| Simulasi Bersih Data | Semua | Mengirim `cleaner_worker`. Proses dapat menghapus notifikasi, bukti baca, dan sesi yang memenuhi syarat. |
| Simulasi Onboarding Toko | Khusus tablet | Mengirim `onboarding_engine`. ID ini tidak memiliki cabang di switch pemicu. Untuk permintaan yang lolos otorisasi, handler berakhir pada respons 400. Tes panduan di baris pertama menggunakan ID berbeda. |
| Simulasi SLA Tiket Helpdesk | Khusus tablet | Mengirim `support_lifecycle`. Dapat menulis pesan, mengganti status tiket, menandai pelanggaran SLA, serta memusnahkan tiket dan lampiran yang sudah mencapai retensi. |

Keempat simulasi umum memakai handler yang sama dengan tombol operasional. Payload belum memiliki mode dry-run, waktu simulasi, kumpulan data contoh, atau pembatas tenant. Uji notifikasi tertarget memang berguna, tetapi harus menerangkan bahwa pesan akan masuk ke akun admin. Repositori memiliki tes teknis retensi dengan SQLite dan storage tiruan. Halaman Sandbox belum menggunakan lingkungan uji tersebut. ### Siapa yang dapat melihat dan menjalankan

Matriks berikut berlaku untuk staf platform yang telah lolos autentikasi dan ketentuan MFA. Ada pengecualian lokal/development untuk akun yang belum mengaktifkan dan belum diwajibkan MFA. Hasil API di tabel diturunkan dari middleware dan rute. Audit tidak menggunakan akun staf produksi.

| Izin efektif | Tampilan saat ini | Keputusan server pada tiga operasi |
|---|---|---|
| Hanya `system:automation:view` | Halaman, tombol Jalankan dan Sandbox terlihat | Ketiganya ditolak tanpa izin pengaturan. |
| Hanya `system:automation:manage` | Halaman dan seluruh tombol terlihat | Ketiganya juga ditolak tanpa izin pengaturan. |
| Hanya `system:settings:manage` | Gerbang modul tidak memberikan akses | Gerbang server memenuhi syarat baca **dan eksekusi**. |
| `automation:view` serta `settings:manage` | Halaman dan tombol terlihat | Server mengizinkan eksekusi walau peran tidak memiliki `automation:manage`. |
| Superadmin | Halaman dan tombol terlihat | Diizinkan lewat hak superadmin setelah melewati gerbang staf/MFA. |

Ketiga bundle menggunakan gerbang UI yang sama untuk baca dan aksi. Pada frontend, respons GET yang gagal bisa meninggalkan angka cadangan atau data lama. Pada backend, satu izin pengaturan menjaga kedua GET dan POST. Perbaikannya adalah menyamakan izin dengan katalog RBAC yang sudah ada, membatasi POST ke pengelola otomasi, dan memberikan alasan eksplisit saat akses ditolak. ### Mengapa Ringkasan dan Riwayat bisa menyesatkan

1. **Sehat sebelum ada bukti eksekusi.** Tracker mengisi status awal `running` dan waktu mulai untuk semua ID. Perhitungan sehat hanya mengecualikan `error` dan `stopped`. Worker yang terlambat, belum pernah berjalan, atau berstatus peringatan dapat tetap terhitung sehat. UI mengganti nol dengan 11 worker atau satu klien SSE dan menampilkan uptime “24 / 7”. [Inisialisasi](../../backend/internal/services/automation_service.go#L69) · [Penghitungan](../../backend/internal/services/automation_service.go#L360) · [Ringkasan mobile](../../frontend/mobile/src/components/PlatformRolePortal.tsx#L13483)
2. **Event, run, dan entitas tercampur.** “Eksekusi 24 jam” menghitung baris log, termasuk boot dan sandbox. Beberapa siklus hanya mengirim heartbeat. Jika hitungan DB kosong/gagal, jalur cadangan tidak selalu membatasi entri ke 24 jam. Pada dormansi manual, siklus mencatat heartbeat sendiri lalu wrapper mencatat lagi. Jumlah toko dipindai juga dipakai sebagai jumlah terdampak. [Metrik](../../backend/internal/services/automation_service.go#L389) · [Wrapper dormansi](../../backend/internal/services/automation_service.go#L543)
3. **Kegagalan parsial tidak selalu sampai ke dashboard.** Siklus pasar terjadwal mengabaikan error empat operasi lalu mengirim heartbeat selesai. Pembersih notifikasi mencatat error kueri di logger, tetapi tetap mengirim heartbeat normal. Retensi tiket menghitung berkas setelah upaya hapus tanpa memeriksa seluruh hasil penyimpanan. Operator belum dapat memakai angka itu sebagai bukti semua data berhasil dihapus. [Agregasi pasar](../../backend/cmd/server/main.go#L193) · [Pembersih](../../backend/internal/services/notification_cleaner.go#L39) · [Lampiran tiket](../../backend/internal/services/ticket_retention_service.go#L108)
4. **Asal tindakan dan identitas pelaku kurang akurat.** UI hanya mengenali `manual` dan melabeli nilai lain “Cron Otomatis”, termasuk `manual_admin` dan `sandbox`. Sejumlah log memakai aktor generik “Admin Portal”. Log onboarding otomatis memakai ID `onboarding` sedangkan kartunya memfilter `onboarding_engine`. Log moderasi dan purge dormansi juga memakai ID peristiwa tersendiri. [Default log](../../backend/internal/services/automation_service.go#L276) · [Log onboarding](../../backend/internal/handlers/notification_handler.go#L1313) · [Render riwayat](../../frontend/mobile/src/components/PlatformRolePortal.tsx#L14190)
5. **Satu klik tidak selalu sama dengan satu pekerjaan.** Kunci manual berupa map dalam memori proses. Jalur jadwal dapat memanggil fungsi siklus secara langsung. Helpdesk serta pemicu retensi tiket juga dapat masuk ke fungsi purge yang sama melalui kunci berbeda. Cakupan perlindungan tumpang tindih antarreplika/jadwal perlu diuji di lingkungan terisolasi. [Kunci manual](../../backend/internal/services/automation_service.go#L336) · [Purge dalam helpdesk](../../backend/internal/services/automation_service.go#L903) · [Purge manual](../../backend/internal/services/automation_service.go#L1063)
